# 如何与论文比较速度

页面始终把两个问题分开显示：

| 指标 | 计量范围 | 用途 |
|---|---|---|
| 采集/编码/解码吞吐fps | 最近2秒实际帧数÷墙钟时间，包含等待 | 检查实时视频能否维持30fps |
| 编码/解码处理速度fps | 最近2秒计量组的帧数÷相应编解码方法累计耗时 | 判断处理余量；相应卡片显示ms/帧 |
| 浏览器角落fps | 实际完成图像解码及canvas绘制的次数÷实际间隔 | 验证显示端的实际播放速度 |
| 采集→canvas中位数 | 编码端采集完成后到第二台浏览器`drawImage()`返回的软件时间戳差；跨机时钟经NTP式校准 | 验收第二台实际绘制时延，不含曝光/屏幕扫描 |
| 模型Mbps | 模型真实码流字节数÷墙钟时间 | 在线压缩载荷吞吐，不包含JPEG及协议开销 |

编码处理耗时包括RGB输入准备、GPU拷贝、颜色转换、模型/原生熵编码、参考状态更新及同步；解码耗时包括模型/原生熵解码、颜色转换、RGB拷贝及同步。二者均不含组帧等待、TCP、JPEG编码或浏览器绘制。HT-S P组固定8帧，首I帧1帧；处理速度按实际组帧数加权，不能用1÷组耗时当成fps。首次加载/图初始化会影响起始读数，稳态报告会先预热。

“采集→canvas”是显示路径的软件测量，不是物理glass-to-glass。每组8帧突发到达显示端后以60fps排空，浏览器每8ms检查最新帧；若帧在解码前已超过475ms采集年龄，则直接跳到下一帧并计入展示丢帧，以保证实际绘制样本的延迟上限。该策略不改变DCVC的30fps采集、编码和解码吞吐。

## 上游计时差异

本项目固定的Microsoft上游commit为cbdae87a5445114cdc7f48816da63ea80bdeac40。其README“Measure compression speed”使用`test_compress_time.py --model_structure hts`，进一步调用`test_video.py`，使用CUDA事件计时；输入读取/输入转换在编码计时前，RGB输出转换在解码计时后。故页面当前“处理速度”范围比上游核心计时更宽，不能直接把差值当作模型退化。

上游还明确列出了已优化的分辨率与设备；640×360和Orin NX不在该列表内。其1080p/4090等结果不能当作360p/Jetson的同硬件对照。正式对照应记录：GPU及内存、JetPack/Torch/CUDA版本、功率模式/时钟/温度/OC事件、分辨率、输入内容、QP、HT-S变体、预热次数、码流熵编码是否启用和计时边界。

此阶段页面提供实时计量与统计导出，未宣称复现论文所有测试条件。固定输入离线基准可用`tools/benchmark.py`，其方法计时同样包含转换与拷贝；不把摄像头等待计入计算速度。

## 与硬件编码器的关系

`tools/compare_codecs.py` 与 H.264/H.265 对比文档已移除。当前项目只保留 DCVC HT-S 自身的吞吐、码率、时延和画质证据。

## 电源异常对结果的影响

2026-10-30编码端MAXN_SUPER下报告over-current。实查OC3计数增加、OC1/OC2为0；解码端三项为0。用户确认编码端适配器19V2.37A（约45W）。这是供电/模块功率限制排查依据，不能仅凭OC3认定适配器损坏，也不能提高保护阈值来消除提示。

发生限速会影响延迟和计算速度；此前实测用来证明功能与播放，不作为无功率限制的论文性能基准。新增硬件验收脚本记录nvpmodel与OC基线，在出现新增OC事件时停止，并可通过`DCVC_REQUIRE_POWER_MODE=25W`要求模式已经生效。

后续检查发现：编码端`nvpmodel -q`虽显示25W，`-q --verbose`却显示GPU上限1173MHz（配置应408MHz）、CPU上限1984MHz（应1497.6MHz）、TPC/FBP掩码未匹配。开机nvpmodel服务因GPU context已创建、要求重启而失败。此次短测OC3由0增至6，保护脚本已停止，未取得25W稳态结果；解码端实际限制正确且OC为0。验收脚本现进一步校验CPU/GPU上限及TPC/FBP掩码，避免只相信模式名称。详见`reports/dual-display-camera-browser-25w-incomplete.json`。

后续结果：编码端安装启动顺序drop-in并重启后，实际限制匹配25W。跨机cuDNN差异造成的画质漂移亦经独立回归修复，详见`quality-consistency.md`。最终两端25W摄像头复测编码/解码29.99fps、第二台浏览器29.9fps、两端OC0；处理速度50.37/47.74fps。旧速度报告的画质未验收，不能单独作为有效画质下的模型对照。2026-11-03低延迟优化后，返回预览时延（组内最老帧）中位数478.9ms、最大490.8ms，最新帧中位数245.3ms，见`reports/dual-host-latency-25w.json`；该口径不含浏览器绘制。同一轮第二台实际Chromium的采集→canvas软件时延中位数425.8ms、p95 475.2ms、最大479.8ms，见`reports/browser-display-latency-25w.json`；显示端丢弃247个超过475ms的过期帧，模型编解码仍约30fps，不含曝光和物理屏幕扫描。
